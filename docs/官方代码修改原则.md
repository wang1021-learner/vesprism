# 官方代码修改原则（现行）

> **生效日期：2026-07-29**  
> **地位：** 二次开发对 `xai-grok-*` / `codegen` 等官方路径的**唯一现行规则**。  
> 旧笔记、归档里「只加不改、禁止改官方」的表述**全部废止**，以本文为准。

---

## 1. 一句话

**可以改官方代码。**  
默认仍优先在桌面壳 / 自建 crate 解决；**当方案明显更好、且收益大于上游同步成本时，应改官方实现**，而不是为了「零 diff」硬绕。

---

## 2. 决策顺序（从优先到放宽）

| 优先级 | 做法 | 适用 |
|--------|------|------|
| **P0** | 先查官方是否已有能力，接到 GUI / `grok-session` | 会话列表、恢复、配置、工具事件等已有 API |
| **P1** | 在 **自建 crate** 解决（`jike-grok-desktop`、`grok-session`、`grok-gui-poc` 等） | 纯 UI、展示策略、键鼠、预览壳 |
| **P2** | **最小侵入**改官方：`pub` 导出、可选字段、hook、feature flag、薄封装 | 只需露出口、不改行为语义 |
| **P3** | **有意修改官方逻辑/协议/工具** | 见下文「好方案」门槛；允许删改重构官方文件 |

P0–P2 是日常默认路径；**P3 不再禁止**，但必须满足第 3 节门槛。

---

## 3. 什么叫「非常好的方案」（允许动官方的门槛）

同时满足越多，越应该改官方，而不是在 GUI 层打补丁：

1. **根因在官方路径**：GUI 层无法正确/稳定解决（协议字段缺失、agent 循环行为错误、工具边界、Windows 硬编码 bug 等）。  
2. **收益清晰**：显著正确性、安全、性能、产品能力，或明显降低长期分叉维护成本。  
3. **改动可描述**：能说清「改了什么 / 为什么 / 合并时怎么合」。  
4. **尽量局部**：优先小补丁、新模块、feature 门控；避免无必要的全文件重写。  
5. **可验证**：有复现步骤或测试/手测路径。  
6. **可回灌**：合并 `upstream` 时知道冲突落点（见 `docs/官方同步-*.md` 的冲突处理习惯）。

**不满足门槛的**，继续用 P0–P2，不要为了「炫技」进官方热路径。

---

## 4. 仍应遵守的约束（与「能不能改」无关）

这些**没有放松**：

| 约束 | 说明 |
|------|------|
| 先读源码再动手 | 协议与行为以真实源码为准，不猜 JSON |
| 先复用官方能力 | 有现成 API 就接，不平行再造 |
| 密钥不进仓 | `.env` / 系统密钥链；不写死 key |
| workspace 依赖 | 与官方交互的 crate 用 `workspace = true` |
| 独立 `GROK_HOME` | 测试与用户数据隔离 |
| 上游不接受 PR | fork 自维护；定期 `git fetch upstream` 再 merge |
| 记录官方补丁 | 改官方时在 PR/笔记/同步说明里写清文件与意图，便于下次合入 |

---

## 5. 改官方时的推荐写法

1. **能加文件就加文件**（新 module / feature），少在巨型 `run_loop` 上散改。  
2. **行为变更**尽量：配置开关、`#[cfg]`、桌面专用 source 标记，避免静默改变 CLI/TUI 默认体验（除非产品明确要求全端一致）。  
3. **注释标明二次开发意图**（短、可搜）：`// jike: <原因>` 或等价标记。  
4. **合 upstream 前**：列出本地官方 diff 清单；冲突时「上游主体 + 回灌本地语义」，不要无脑 `ours`/`theirs`。  
5. **Design / agent 能力**若要多端复用：优先进官方（见 `docs/独立Design产品完整方案.md` 的「能力进官方、体验在桌面」）。

---

## 6. 路径归属（便于判断）

| 路径 | 性质 |
|------|------|
| `crates/codegen/**`、`xai-grok-*` 等 | **官方**；改动适用本文 |
| `crates/jike-grok-desktop/**` | **自建**；可自由迭代 UI/壳 |
| `crates/grok-session/**`、`grok-gui-poc/**` | **自建桥接**；优先放这里，必要时再下沉官方 |
| 根 `Cargo.toml` members / workspace 依赖 | 允许追加；与官方版本对齐 |

---

## 7. 废止声明

以下表述**不再作为约束**（历史文档可保留原文，但决策以本文为准）：

- 「只加不改、不删除、不重构官方代码」作为**硬性禁令**  
- 「不碰官方 TUI / 官方 crate」作为**绝对禁止**  
- 「全文遵守只加不改官方」  

**替代表述：**

> **默认可在壳层完成；有更好的、可维护的方案时，允许并鼓励改官方代码。**
